## 优先问题

### P1：参数类型与描述冲突

H3 `input_reference` 的 Schema 是 string，但描述允许 `{ "image_url": "https://..." }` 对象。这会让客户端代码生成、参数校验和实际调用产生歧义。

建议：用 oneOf 明确字符串和对象两种结构，每种配一个示例；不要只把对象结构写在说明文字里。

### P1：必填、默认值和条件必填未区分

H3 与可灵 `duration` 同时处于 required 列表并配置 default: 5。二者在 OpenAPI 中可以同时存在，但读者无法据此判断“服务端默认 5 秒”还是“客户端必须显式传 5”。需要逐渠道核对后明确可否省略。

H3 的文生视频 ratio 条件必填、首尾帧与参考素材的互斥、content 文本能否替代 prompt，主要靠长段说明，参数表的 required 标记不足以表达条件。

建议：增加按输入模式划分的表格：文生视频、首帧、首尾帧、参考生视频，分别列必填、可选、禁止组合及示例。

### P1：嵌套字段只展示类型，缺少可操作说明

参数 Schema 检查发现：

- Responses：model、instructions、max_output_tokens、reasoning、previous_response_id 等多个字段没有逐项 description。
- Claude Messages：messages、system、max_tokens、thinking、tools 等多个字段缺少逐项 description；部分对象没有明确 properties。
- 豆包长文本语音：user、req_params 未给出字段级说明。
- 千问及 MiniMax 语音：input 对象缺少字段级说明。

建议：展开嵌套字段，至少说明字段层级、数据类型、是否必填、取值范围、默认行为、可用模型、互斥关系和完整输入示例。把 JSON 路径写清楚，例如 `input.text`，不要只写“文本”。

### P1：错误响应分支不完整

导入源中，24 个模型接口里有 23 个未声明 401、23 个未声明 429；147 个系统管理接口均未声明 401/403（并非所有接口都需鉴权，应按实际路由区分）。

这不代表接口不会返回这些错误，而是文档缺少对应约定。

建议：按接口鉴权和实现补齐错误示例；区分 HTTP 失败、异步任务最终失败、余额不足、令牌额度耗尽、平台限流及上游限流。不要给所有接口机械套同一组错误码。

### P2：范围限制没有完整进入 Schema

部分长度、时长、参考素材数量只写在 description，未形成 min/max、maxItems、maxLength 等结构化限制。

建议：能统一确定的限制写入 Schema；随模型或渠道变化的限制以模型/渠道支持矩阵说明，避免一个公共 enum 让用户误认为所有模型都支持全部值。

### P2：异步接口缺少完整操作闭环

已有任务查询页给出状态和大致轮询间隔，但仍应统一补充：提交响应中的任务 ID 字段、查询鉴权、终态、错误位置、下载鉴权、URL 有效期、退避轮询和失败时如何核对账单。

“提交返回 200”不等同于“生成成功”。退款描述应以实际结算规则为准，避免脱离渠道/计费方式作绝对承诺。

### P2：接入凭据需要按接口族明确

模型请求使用站点 API Key；面板与管理接口使用登录 access_token 或系统访问令牌，管理员操作还需相应角色。已有两个不同鉴权组件，但每个目录仍应有清楚的获取说明及失败示例，避免用户把模型 Key 用于系统管理接口。

### P2：模型和渠道差异容易被总述掩盖

官方 H3 与 H3-Fast 工作流版不能共用一张无条件参数支持表。参考视频、mode、分辨率、参考图数量等应按已验证渠道说明；“不支持的参数会忽略”不可当作全站通用约定，部分适配器会返回 400。

## 建议修订顺序

1. H3 / H3-Fast：模式矩阵、素材字段、类型冲突及条件必填。
2. Responses / Claude：嵌套参数、工具调用、流式示例与错误响应。
3. 语音接口：input/req_params 层级、情绪参数、音色参考与同步/异步区别。
4. 图片及其他视频：分辨率/比例/数量约束、异步查询下载闭环。
5. 系统管理接口：按公开、登录用户、管理员、超级管理员分组补齐鉴权与响应约定。

首次检查时尚未批量重写。后续已对照本站实现修订并发布 24 个模型接口，详见 `apifox/README.md` 和核对结果；147 个系统管理接口未在本轮逐字段重写。
